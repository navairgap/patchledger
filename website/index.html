01 — Overview

One ledger for every scanner

One tool finds secrets, another flags vulnerable dependencies, a third catches insecure code. PatchLedger imports all of their reports — or runs them for you — and merges everything into a single, deduplicated, scored ledger that persists across scans.

in

Import or scan

SARIF 2.1.0, semgrep, gitleaks, bandit, and pip-audit reports — or live execution of the tools already on your machine. Missing tools are recorded, never hidden.

≡

Normalize & deduplicate

Every finding gets a stable fp2 fingerprint and one severity scale. Duplicate sightings merge; every occurrence keeps its own evidence.

✓

Verify the fix

A finding disappears from the new scan? Verification checks scanner coverage before saying "fixed" — otherwise it stays honestly inconclusive.

out

Report anywhere

JSON, Markdown, self-contained dark HTML, and SARIF for GitHub code scanning — with coverage honesty baked into every format.

02 — The problem

Tool sprawl, manual triage, unverifiable fixes

The scanners are fine. The workflow around them is broken.

✕

Five tools, five formats, one spreadsheet

Severity scales disagree, paths disagree, duplicates multiply. Triage means reconciling five dashboards by hand — and important findings drown.

?

"Is it fixed?" is a guess

Most pipelines declare a finding resolved the moment it stops appearing — even if the scanner never ran, crashed, or never covered that file. False "resolved" states are how regressions reach production.

⏳

No memory between scans

Without history you cannot tell "persistent since March" from "new this week" — and a silently regressing fix looks exactly like a fresh finding.

PatchLedger's answer: a local-first ledger with deterministic fingerprints, explainable risk scores, and patch verification that demands evidence. Nothing is marked fixed on a guess.
03 — Features

Built for real remediation work

Eight capabilities that make the difference between a scan and a fix.

01

Honest scan coverage

Every scan records which tools ran, failed, or were missing. Reports are labelled incomplete when coverage isn't full — never silently optimistic.

02

Stable fingerprints

Versioned fp2 identity built from scanner, rule, path, message, and snippet — stable across line shifts, new exactly when the flagged code changes.

03

Explainable risk scores

Deterministic 0–100 scores where every adjustment is listed: severity base, scanner confidence, evidence quality, category weight. No invented CVSS.

04

Scan history & diffs

Compare any two scans: new, persistent, reintroduced, changed severity, moved location — plus an audit trail of every status transition.

05

Local remediation knowledge

Offline guidance per rule family: why it matters, consequences, a concrete fix, a secure pattern, references. Advice stays separate from evidence.

06

Offline AI review prompts

Generate a reviewer-ready prompt from selected findings — with explicit rules against inventing evidence. Bring your own reviewer, human or AI.

07

Secret redaction on ingest

gitleaks matches, PEM blocks, and common token formats are redacted before anything is stored or rendered. Redaction is hygiene; rotation is the fix.

08

CI-ready exit codes

--fail-on high exits 2 on threshold hits, --strict exits 3 on incomplete scans. Documented, tested, GitHub-Actions ready.

04 — How it works

From raw scanners to verified fixes

Six deterministic stages. No magic, no black boxes.

  1. Scan or importRun installed scanners against the repo, or import existing reports. Every tool's participation is recorded.
  2. NormalizeOne finding model: mapped severity, confidence, category, redacted evidence, remediation guidance. Scanner metadata preserved verbatim.
  3. Fingerprint & dedupDeterministic sha256 identities merge duplicate sightings while every occurrence stays visible as evidence.
  4. Score & storeExplainable risk scores attach to each finding; the scan commits to your local SQLite ledger as an immutable observation.
  5. Compare & verifyThe next scan diffs against history. Disappeared findings become resolution candidates — verified only with real coverage.
  6. ReportJSON, Markdown, self-contained HTML, or SARIF — each format stating exactly what coverage the scan had.
05 — Security scanning

Run what you have — honestly

PatchLedger invokes the scanners it finds on your machine and records each one's status. A missing tool is a fact, not a failure: the scan is labelled incomplete and no resolution claims are built on top of it.

No downloads, no surprises. PatchLedger never fetches or executes scanner binaries on its own — it only runs tools you installed. patchledger doctor shows exactly what it can see.

06 — Finding normalization

One consistent data model

Every scanner's raw result maps through explicit, documented tables. Severity is never invented; unknown values stay unknown; original scanner metadata rides along untouched.

map

Explicit severity tables

semgrep ERROR, bandit HIGH, SARIF error — one normalized scale, with the raw value kept for audit.

fp2

Content-stable fingerprints

sha256(scanner, rule, path, message, snippet) — stable across line shifts, versioned, documented with its limits.

≡

Dedup with receipts

Identical findings merge into one entry; every merged sighting stays listed as an occurrence with its own evidence.

***

Secrets redacted on ingest

gitleaks matches, PEM blocks, and common token formats are redacted before storage — and again in every renderer.

07 — Patch verification

Never call it fixed without proof

After you change code and rescan, a vanished finding is only a resolution candidate. It becomes fixed and verified only when every scanner that ever reported it ran successfully against the same target. Otherwise it stays inconclusive — and inconclusive is never treated as fixed.

Why it matters: an honest inconclusive costs a re-run. A false fixed costs a breach.
fixed_verified All reporting scanners ran successfully on the same target — proof attached.
still_present The fingerprint reappears in the latest scan.
reintroduced Was verified fixed — and has come back. Escalated loudly.
inconclusive Missing or failed scanner, imported report, or different target — the reason is recorded.

10 — Architecture

Modular, local-first, boring on purpose

Python 3.10+, Typer, Pydantic, SQLite, Rich. Three runtime dependencies. No server, no telemetry, no network after installation.

11 — Installation

Up and running in two minutes

Python 3.10+ required. Everything else is optional and reported honestly.

01

Install PatchLedger

$ pipx install patchledger
# or: pip install patchledger
# dev: pip install -e ".[dev]"
02

Check your scanners

$ patchledger doctor
# widen coverage: pip install bandit
# pip-audit semgrep · gitleaks/trivy: system pkg
03

Scan your repo

$ cd your-project
$ patchledger init
$ patchledger scan .
04

Verify a fix

$ patchledger scan .
$ patchledger verify
$ patchledger report --format html
